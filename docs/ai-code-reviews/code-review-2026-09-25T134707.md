## Recommendation: needs_changes

Three high findings and six mediums. The security lens passed clean. The
highest-impact defect: app.tsx re-implements GitHub remote parsing with a
greedy regex instead of using the resolveRepoSlug it already imports, so
.git-suffixed remotes produce chip hrefs that GitHub 404s (verified live)
while the status-dot path keeps working. Second high: better-sqlite3 is
imported by shipped server code but declared only as a devDependency, which
can break fresh installs at load instead of degrading. Fix both before
merge; the mediums are small and mechanical.

---

### security — passed

No actionable vulnerabilities. SQL is parameterized end to end; the IN-list
placeholders derive from array length, never values. The DB path is fixed
(no user input), opened read-only. Chip hrefs are constrained at
construction: GitHub URL hrefs are pinned to the literal https://github.com
host with owner/repo restricted to safe character classes, so javascript:
or data: hrefs cannot be produced from thread titles or branch names. All
chip text renders as React text children (HTML-escaped). No secrets. No
cross-tenant surface.

### style — warning

Findings: (high) duplicated remote parser in app.tsx disagreeing with
resolveRepoSlug on .git suffixes; (medium) unused `repo` prop on
TicketChip; (medium) bare catch in readGitHubStatuses hides unexpected
errors with nothing logged; (medium) four new files missing trailing
newlines; (low) status type shape duplicated inline in three places;
(low) branch derivation + ref scanning duplicated between app.tsx and
thread-card.tsx; (low) visibleRefKey string round-trip; (low) unexplained
500 cap.

### logic — warning

Findings: (high) chip hrefs 404 for .git-suffixed remotes, dot path
unaffected (verified live, no redirect); (medium) tracker_status silently
drops all statuses for a repo when the visible batch exceeds the 500-number
zod cap, with an empty rejection handler and no signal; (medium)
repoBaseByProject fetched once on mount, never retried, so a startup race
or transient failure kills the whole chip feature for the session; (low)
HASH_REF misses the second ref in glued forms like #1#2 (lookbehind fix);
(low) ticketStatuses accumulates stale repos; (low) ssh remotes produce no
base though resolveRepoSlug supports them. Verified positives: tsc clean,
53/53 tests pass, sqlite handle closed in finally, no sqlite in the client
bundle, matchAll regex-clone safety, effects' cancelled flags correct.

### docs — warning

Findings: (medium) KEY_REF comment claims a lookbehind but the regex uses a
leading \b; (medium) inline comment misattributes the (?![-\w]) lookahead's
job (it rejects trailing hyphens like PROJ-123-4); (medium) the 500-number
cap is undocumented; (low) GitHubItemStatus lacks a doc comment; (low)
GITHUB_CACHE_DB comment omits the $HOME join; (low) visibleRefKey
round-trip uncommented. Module headers otherwise strong.

### memory — warning

One finding: ticketStatuses is merged rather than replaced per snapshot, so
entries for refs that leave the visible set persist for the session (slow
unbounded growth, stale-dot risk). Batching design otherwise sound; sqlite
connection closed in finally; no leaks.

### project-memory-conformance — warning

Findings: (high) better-sqlite3 imported by shipped runtime code but
declared as a devDependency, breaking fresh installs; (low) shipped
tracker_status contract ({repo, numbers} → kind/state) deviates from the
plan's documented {repo, refs} → title/updatedAt without a plan note;
(low) README omits ticket chips, link-out, and the cache-read disclosure.
Coverage-matrix rows conform and cite tests that exist.
